### 0.（最高优先级）Lane2 refresh-v1 / Lane3 状态机被 2026-09-03 缺失 bar 毒化——自 0904 起失效

**现象**：`v1_signal_daily.parquet` 与 `trend_transition_state_{date}.parquet` 在最近所有交易日（0903→0911）的 `pos60/pos120/pos360` **对所有 1309 只 ETF 全部等于 50.0**，`long_term_bottom` / `confirmed_long_term_bottom` **全部为 False**。因此：

- Lane3 状态机「看不见底部」：全市场没有 BOTTOM，只能把绝大多数资产放进 POST_TRANSITION（970 只），再凭 09-04 前后那次「假 exit」派生出一批 FIRST_EXIT/EARLY（24/28）——**这些是伪影，不是真实的状态切换**。
- 三 Lane 表（`three_lane_20260911.parquet`）的 Lane 2 列（`long_term_bottom` / `bottom_state` / `pos120`）同样全空，ETF 报告 ④ 的 Lane 2 视图不可用。
- 0910 与 0911 的 Lane3 分布逐格相同（970/185/28/24/1/101），正是「状态被冻结」的症状。

**根因（可复现）**：raw 缓存里 **2026-09-03 全市场缺 bar**（1598/1609 只 ETF 的 close 为 NaN；该问题 0908.md 已发现并建议修数，但至今未修）。而 `src/research/etf_bottom/state_odds.py::daily_state_series` 用
```python
lo = close.rolling(w, min_periods=w).min()
hi = close.rolling(w, min_periods=w).max()
pos = (close - lo) / (hi - lo) * 100.0
df[f"price_pos_{w}"] = pos.where((hi > lo), 50.0)
```
处理：窗口内只要有一个 NaN，`min_periods=w` 无法满足 → `lo/hi` 为 NaN → `(hi > lo)` 为 False → `where` 把该日 `pos` 写成 **50.0**。由于 09-03 的 NaN 会在这个窗口里停留整整 w 天，`pos60` 被毒化到 ~2026-12，`pos120` 到 ~2027-03，`pos360` 到 ~2028-02——**除非修数，Lane3 在一年以上都处于失效状态**。

**对照（为什么 Layer A 看起来是对的）**：Lane2 的 `--scan` 走的是 `price_map.compute_row`，它用 `close.iloc[-w:].min()`（pandas **skipna** 默认），NaN 会被自动跳过，所以 `scan_{date}` 的 DEEP/RECOVERING/ltb 是**正确的**。于是出现同一系统内两个 Lane2 口径打架：**scan 说全市场 84 只长期底部，three_lane 说 0 只**。

**修复建议（按优先级）**：
1. **修 raw 的 2026-09-03 bar**（从源端重拉或补数），并重算 `v1_signal_daily` / `trend_transition_state`。这是根因，0908.md 已提出，必须落一条 fix。
2. **让 `daily_state_series` 对缺失 bar 鲁棒**：rolling 前 `df = df.dropna(subset=["close"]).reset_index(drop=True)`，或改为与 `price_map` 一致、用尾部窗口 `skipna` 的 min/max；同时把 `where((hi>lo), 50.0)` 改为**缺失时留 None 而不是 50.0**——50.0 与真实的「中位位置」不可区分，是最危险的静默污染。
3. **加完整性断言**：`refresh_v1_signal_daily` 在落盘前校验「最近交易日的 pos 非全 50 / 非全 NaN」，命中即告警（类似 SW 的 coverage gate）。
4. **Lane3 增加自检**：若 `confirmed_long_term_bottom` 全市场为 False 或状态分布跨日语料完全不变，报告应显式标 `state_data_suspect`，而不是照常发布。

### 1. select 连续第四日 lane_less（跨四份复盘的同一建议）

run-day 内 select 先于 three-lane，③A 的 Lane2 可靠性 gate 在首次运行日不参与。本日还叠加了六.0。建议：run-day 在 three-lane 生成后补一次 select（幂等，几秒），或在 `final-check` 对 lane_less 的候选补做复检。

### 2. 选车 direction dedup 平局按行序取代表（新发现，机制性）

`_dedup_etf` 只按 `selection_score` 排序，而该分数是 amount 经 log_threshold 后**封顶 100**；当同方向多只 ETF 都顶到 100 时，稳定排序保留原始行序（`rotation` 按 `fund_code` 升序），**于是方向代表由 code 大小决定，而非真实金额**。本日实测：

- 通信方向 eligible 7 只中，**159583 通信ETF富国（amount 5.86 亿）成为代表**，而 515050 通信华夏（13.9 亿）、515880 通信国泰（**43.1 亿**）、159994 通信银华（3.66 亿，score 86.5）全部被判 `dedup_lost`。
- 结果：**AI 通信链 RPS15 90+ 的真载体被排除**，代表 159583 的 leadership=NON_CORE、signal=WAIT，最终 AI 0 推荐。

建议：`_dedup_etf`/`best_per_dir` 在 score 相同时以 **amount（或 amount + rps15）二次排序**，杜绝行序决定代表。

### 3. AI 执行链 `LEADER_PRIORITY → ETF_FALLBACK` 的语义需明确

AI 结构判断为「龙头主导」，但当前 Layer③ 发布为 ETF-only（个股不进候选），于是 execution 必然降级为 `ETF_FALLBACK (NO_ELIGIBLE_STOCK)`，而 ETF_FALLBACK 模式下系统似乎只推 primary_etf（562590，RPS15 2.4），把真正过门的通信 ETF 留在观察池。这使「AI 已确认 + 通信链 RPS15 90+」对用户零可执行输出。建议：ETF_FALLBACK 下应把「同方向 eligible + 过趋势门」的 ETF 提升为候选，而不是锁死在 structural leader 车辆上。

### 4. 推荐标的自身带数据质量标记

159611 的 `data_quality_flags=["INSUFFICIENT_HISTORY"]`、`technical_diagnostics.momentum=UNKNOWN`（ΔRPS15 缺失）。BUY 标的的核心动量维度是 UNKNOWN，属于可观测性问题；建议把 ΔRPS15 的历史不足与输入缺失区分展示。
