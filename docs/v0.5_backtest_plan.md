# v0.5 回测开发计划（结构性收敛版）

> 状态：评估稿（尚未实施）
> 目标：回答唯一问题——**如果过去严格按照 AKSignal 每日生成的信号执行，结果会怎样？**
> 范围约束：不开发海龟完整策略、参数优化器、多资产组合、蒙特卡洛模拟。
> 本版相对初稿的收敛：明确研究对象、规则边界、验收口径，避免开发中反复重新解释。

## 0. 一句话结论

> **AKSignal v0.5 的目标不是先构建复杂回测引擎，而是建立可信的历史研究链路：用共享规则函数重放历史信号，通过真实产物校验重放一致性，再用事件研究判断信号价值，最后用最小交易模拟验证其可执行收益。v0.5 不处理组合风险优化。**

## 1. 核心判断与硬边界

**瓶颈不是回测引擎，是信号历史。** 要回答「如果过去严格按 AKSignal 信号执行会怎样」，前提是存在历史信号；而 AKSignal 自己的信号产物只有约 2 周历史，必须先按相同规则用现价数据**重放**出来。

以下为 v0.5 硬边界，不在开发中重新解释：

| 结论 | 处理 |
| --- | --- |
| 现有历史信号不足，必须重放 | 保留 |
| Replay 与 daily pipeline 分离 | 保留 |
| 两者共享规则函数 | 保留并强化（见 §5 parity 验收） |
| 先做事件研究，再做交易模拟 | 保留 |
| 组合管理推迟到 v0.6 | 保留 |
| 不照搬海龟参数，只继承结构 | 保留 |
| 行业是主历史轴，ETF/个股作为辅助 | 保留 |
| T 日信号、T+1 成交 | 保留 |
| 不可成交不能静默忽略 | 保留 |

## 4. 架构：Replay → Signal Store → Strategy Policy → Event / Trade

### 4.1 模块职责分离

```
历史价格
  → Replay Engine
  → Historical Signal Store
  → Strategy Policy
  → Event Study / Trade Simulation
```

| 模块 | 回答的问题 |
| --- | --- |
| Replay Engine | 历史某一天，Layer①–③会产生什么状态？ |
| Strategy Policy | 面对这些状态，策略决定采取什么动作？ |
| Execution Engine | 这个动作在市场上如何成交？ |

第一版 Strategy Policy 保持很薄：

```text
WATCH / QUALIFIED     → HOLD_CASH
首次 RECOMMENDED      → ENTER
持续 RECOMMENDED      → HOLD
退出 RECOMMENDED      → EXIT
```

增加这一层不是为了现在做策略库，而是避免把「信号」和「交易动作」绑定死。未来同一套历史信号可测试：仅 ETF / 仅个股 / RECOMMENDED 首次进入 / QUALIFIED 提前进入 / 信号退出 / MA20 退出 / ATR 退出。

### 4.2 区分三类「历史」

| 类型 | 含义 |
| --- | --- |
| Observed History | 当时真实运行并保存下来的产物 |
| Replayed History | 现在使用历史行情和当前规则重新生成 |
| Synthetic Strategy History | 在重放信号之上套用策略规则生成的交易动作 |

三者不能混用。回测报告必须标注：

```text
signal_origin = replayed
rule_version = v0.4.3
configuration = current_static_theme_mapping
```

避免让人误以为 2023 年系统当时真的产生过这些信号。

### 4.3 历史信号 schema

历史信号产物同时保留「状态」和「决策依据」，统一 schema：

```text
trade_date
entity_type
entity_code
theme
layer
rps15
trend_score
trend_state
confirmation_status
selection_status
recommended_action
signal_reason
source_trade_date
data_status
rule_version
config_hash
```

两个关键字段：

- **`rule_version`**：信号由哪个规则版本产生，如 `selection_v0.4.3`。
- **`config_hash`**：当时使用的主题、资产池、阈值配置哈希。否则修改 `themes_two_directions.yaml` 或确认阈值后，同一历史区间会得到不同结果，却无法解释差异。

## 5. 规则一致性（Parity）——S0 验收核心

文档写了「共享规则函数」，还必须给出**一致性测试**。这是 S0 最重要的验收标准：

> 对已有正式产物日期，Replay Engine 的输出必须与 daily pipeline 的正式输出一致。

现有可校验日期：

- ETF rotation：2026-07-31、2026-08-03；
- industry confirmation：已有 3 个日期；
- selection：已有正式日期；
- account candidates：2026-07-22 起的 7 个日期。

新增 `replay_parity_test`，比较字段：

```text
trade_date
asset_code / industry_code
rps15
trend_state
confirmation_status
selection_status
recommended_action
```

数值字段允许合理浮点误差，**状态字段必须完全相同**。否则 Replay 即使能跑十年，也不能证明它重放的是当前 AKSignal。

## 6. 三层回测可行性

### 6.1 信号层（事件研究）—— v0.5.1，最便宜、最先做

验证信号本身有无预测价值，不涉及完整交易账户。

- 数据充足：行业 1999+、ETF 2020+、个股 2018+ 都够算前向收益
- 不需要完整交易账户，不需要撮合
- 行业层做主历史，ETF 信号辅助（2020+）

### 6.2 交易层 —— v0.5.2，依赖信号重放完成

按明确规则模拟买卖，规则集见 §11。

### 6.3 组合层 —— v0.6，明确推迟

ATR 仓位 / Core-Quality 权重 / 最大持仓 / 空仓比例 / 是否加仓 / 组合波动控制全部属于 Layer 4，必须先有交易层结果才有意义。

## 8. 实验边界：主题回放起点 + 两类研究

不要只写「合理起点」，正式配置：

```yaml
themes:
  ai_infrastructure:
    replay_start_date: 2023-01-01
  high_cashflow:
    replay_start_date: 2018-01-01
```

同时区分两种研究，**不能混成一条收益曲线**：

| 研究 | 历史范围 | 验证内容 |
| --- | --- | --- |
| 行业规则长期有效性 | 申万二级 1999–2026 全历史 | RPS confirmed → 后续收益（通用行业趋势规则） |
| 当前主题策略有效性 | AI 基础设施 2023+；高现金流 2018+ | 当前策略配置（主题 + 资产覆盖完整期） |

## 9. ETF 幸存者偏差约束

v0.5 不试图彻底解决，但必须采用以下约束：

```text
1. ETF 只能在实际上市日期之后进入横截面；
2. 历史日期不得使用尚未上市 ETF；
3. 结果标记 current-master survivorship bias；
4. ETF 结果不作为长期历史有效性的唯一证据；
5. 主结论优先来自行业层。
```

输出每日横截面覆盖，避免把 2020 年少量 ETF 与 2026 年 1500+ 只直接等量比较：

```text
trade_date
eligible_etf_count
priced_etf_count
coverage_rate
```

## 10. 事件研究：事件定义与度量

一个行业可能连续 15 天保持 `confirmed`，不能每天都作为独立事件（样本严重重叠）。第一版定义三类事件：

| 事件 | 定义 |
| --- | --- |
| Entry Event | 非 confirmed → confirmed |
| Persistence Event | confirmed 连续维持 N 日 |
| Exit Event | confirmed → 非 confirmed |

Selection 同理：`非 RECOMMENDED → RECOMMENDED` / `RECOMMENDED → 非 RECOMMENDED`。

**事件研究以状态转换事件为主**，而非每天状态快照。输出：

- 事件数量、非重叠事件数量；
- 5/10/20/60 日收益、基准超额收益；
- 胜率、中位数收益；
- 最大有利变动（MFE）、最大不利变动（MAE）。

仅看平均收益容易被少数大涨事件扭曲。

## 11. 退出规则：ExitPolicy

退出规则拆成独立策略，不在 S2 前一次性写死：

```text
signal_exit      退出 RECOMMENDED
ma20_exit        close < MA20
fixed_stop_exit  固定止损
atr_stop_exit    ATR 止损
```

- **v0.5.2 第一轮只选 `signal_exit` + `ma20_exit`**；
- 固定止损和 ATR 止损后续再进入实验（引入更多参数和盘中成交语义）。

当前没有显式 `SELL`，不要为回测临时制造语义不清的 SELL。明确：

> **EXIT 是策略动作，不是原始 Selection 信号。**

即 `Selection 退出 RECOMMENDED → Strategy Policy 生成 EXIT`。

## 12. 数据质量门控

Replay 遇到数据缺失不能继续静默计算。每日信号带 `data_status`：

```text
current
stale
missing
insufficient_history
not_listed
```

规则：

```text
missing / insufficient_history / not_listed → 不产生交易信号
```

行业横截面最低覆盖率：

```yaml
minimum_cross_section_coverage: 0.95
```

覆盖不足的日期：

```text
replay_status = degraded
```

事件研究可以保留 degraded 日期，但**不能进入正式交易回测**。

## 13. 开发计划（五步）

### S0.1：规则函数提取

先确认现有逻辑能被纯函数调用，而不是先循环历史日期。提取：

```text
calculate_rotation_state(...)
calculate_industry_confirmation(...)
calculate_selection_state(...)
```

要求：输入显式；不联网；不读「最新日期」；不隐式依赖当前时间；不直接写报告；同样输入得到同样输出。

### S0.2：Replay Engine

```text
输入：start_date / end_date / rule_version / config_snapshot
输出：historical_signals.parquet + replay_manifest.json
```

### S0.3：Parity Validation

对已有真实产物日期逐字段对比，输出 `replay_validation.json`。**只有 parity 通过，S0 才完成。**

### S1：Event Study

以状态转换事件为基础，计算前向收益、超额收益、MFE、MAE 与分布。

### S2：Trade Simulation

只实现：

- 首次 RECOMMENDED 入场；
- T+1 开盘执行；
- `signal_exit` / `ma20_exit`；
- 固定等权；
- 手续费、滑点；
- 不可成交显式记录；
- 暂不做多资产风险优化。

## 14. 验收标准

### v0.5.0 Replay

```text
1. 支持 start_date / end_date；
2. 全流程离线；
3. 严格 as-of；
4. 历史未上市资产不进入横截面；
5. 每条记录包含 rule_version 和 config_hash；
6. 相同输入输出完全一致；
7. 已有正式日期 parity 通过；
8. 缺失数据不会静默生成正常信号；
9. 输出覆盖率与降级日期；
10. 运行结果具有 manifest。
```

### v0.5.1 Event Study

```text
1. 基于状态转换事件；
2. 支持 5/10/20/60 日；
3. 同时计算绝对收益和基准超额收益；
4. 输出均值、中位数、胜率、MFE、MAE；
5. 区分行业、ETF、个股和主题；
6. 能识别样本重叠；
7. 结果可复现。
```

### v0.5.2 Trade Simulation

```text
1. T 日收盘信号，T+1 开盘执行；
2. 入场、持有、退出状态机明确；
3. 不可成交订单显式记录；
4. 包含手续费和滑点；
5. 输出 orders、trades、positions、equity；
6. 输出收益、回撤、Sharpe、胜率、盈亏比；
7. 能与 HS300 和简单趋势基准比较；
8. 暂不包含 ATR 仓位和组合优化。
```

## 15. 第一轮开发任务（P0-1..P0-7）

不要直接创建完整 `src/backtest/`。先做代码勘察和规则解耦：

```text
P0-1 找到 ETF rotation 的纯计算入口及隐式「最新日期」依赖
P0-2 找到 industry confirmation 的计算入口及 drilldown 耦合
P0-3 找到 Selection 状态生成的纯计算入口
P0-4 定义 historical_signals schema
P0-5 建立 replay parity fixtures
P0-6 实现单日期 replay
P0-7 再扩展日期区间循环
```

**首个提交目标**（建议信息）：

```text
feat(replay): add deterministic single-date signal replay foundation
```

> 指定一个已有正式产物的 `trade_date`，纯离线重新计算，并证明结果与正式产物一致。

这一步通过后，再开始区间重放。否则直接跑 2018–2026，只会更快地产生一大批无法确认是否正确的数据。

## 16. 风险（保留自初稿）

1. **Survivorship bias**：ETF master 是当前快照（§9 约束处理）；行业（申万维护）最干净；个股池是固定清单，无此问题。
2. **Theme 固定化应用到历史**：用今天配置回放远古无意义（§8 replay_start_date 约束）。
3. **信号退出未定义**：§11 ExitPolicy 在 S2 前定死。
4. **撮合现实性**：一字涨停买不进、跌停卖不出，最小版本按「次日开盘价成交」标记不可成交，不静默忽略。
5. **结论边界**：v0.5 回答「信号有无预测价值 + 简单执行能否盈利」，不是「完整策略可不可用」。
